# 跨平台环境与复现方案

| 项目 | 内容 |
|---|---|
| 文档编号 | T06-ENV-001 |
| 版本 | v1.0 |
| 关联决策 | `docs/adr/0004-容器化与多架构环境策略.md` |
| 基本结论 | 采用双架构原生容器，正式评估统一在中央处理器上执行 |

## 1. 问题说明

组内设备分布如下。

| 成员环境 | 处理器架构 | 主要问题 |
|---|---|---|
| macOS | ARM64 | 无 CUDA 设备；MPS 与中央处理器数值行为不完全一致；外置卷挂载性能较低 |
| Windows 10 与 11 | AMD64 | 需启用 WSL2 才能运行 Linux 容器；中文路径与长路径限制 |
| Ubuntu | AMD64 | 相对稳定，但系统级科学计算库版本冲突较常见 |

若各组员自行安装依赖，将出现以下三类问题。

第一，环境不可移植。依赖版本不同会引起接口变更。例如 scikit-learn 部分参数废弃、NumPy 2.x 与旧版 OpenCV 存在二进制接口冲突。

第二，指标不可比。不同设备的浮点实现与线程数不同，可能导致结果在小数第三位产生差异，进而被误判为实现错误。

第三，ARM 架构缺少预编译包。部分依赖在 ARM64 上无预编译包，安装时触发源码编译，耗时长且失败率高。

因此，本项目将运行环境作为交付物管理，而非由各组员自行维护。

## 2. 方案比较与选择

| 方案 | 一致性 | 首次搭建耗时 | 运行性能 | 维护成本 | 采用情况 |
|---|---|---|---|---|---|
| 多架构原生容器 | 高 | 30 至 60 分钟 | 接近原生 | 低 | 主方案 |
| 按平台锁定依赖 | 中等 | 约 20 分钟 | 原生 | 中等，每个平台一份锁文件 | 备用方案 |
| 组内共用 Linux 虚拟机 | 很高 | 约 60 分钟 | 取决于虚拟机规格 | 中等，存在单点故障 | 长任务备用 |
| 各自安装依赖 | 低 | 约 10 分钟 | 原生 | 高，问题反复出现 | 仅限个人探索 |

方案确定为：以多架构容器为主，Linux 虚拟机为辅，按平台锁定依赖作为无法安装容器时的临时方案。各自安装依赖仅允许用于个人探索，其结果不得写入报告。

## 3. 目标环境

| 项目 | 规格 |
|---|---|
| 基础镜像 | `python:3.11-slim`，官方支持 linux/amd64 与 linux/arm64 |
| Python 版本 | 3.11。不使用 3.13 及以上版本，以免科学计算包缺少预编译包 |
| 计算设备 | 中央处理器。正式评估固定使用该设备 |
| 依赖分层 | 基础依赖、深度学习依赖与网页依赖三份文件 |
| 镜像标签 | `docnorm:cpu-arm64`、`docnorm:cpu-amd64` |
| 预计体积 | 1.2 至 1.8 GB，安装中央处理器版 PyTorch，不含 CUDA 组件 |

## 5. 容器方案

### 5.1 镜像构建文件

构建文件为 `env/Dockerfile`。要点如下。

1. 基础镜像固定 `python:3.11-slim`。
2. 先安装基础依赖，再安装中央处理器版 PyTorch，利用层缓存减少重建时间。
3. 默认安装 `fonts-noto-cjk`，保证图表中文正常显示。网络受限时可使用 `--build-arg INSTALL_CJK_FONTS=0` 先完成依赖冒烟，出图前再补齐字体。
4. 通过 `.dockerignore` 排除 `data/raw_samples`、`data/release`、运行产物与模型权重，避免构建上下文包含数 GB 样本。

命令行入口在阶段一实现后启用，当前默认命令为环境自检脚本。

### 5.2 构建方式

```bash
# ARM 架构设备，本机原生构建
docker build --platform linux/arm64 -f env/Dockerfile -t docnorm:cpu-arm64 .

# x86 架构设备
docker build --platform linux/amd64 -f env/Dockerfile -t docnorm:cpu-amd64 .
```

若环境已安装 buildx 组件，可改用 `docker buildx build --platform ... --load`。本机当前的 Docker 客户端未包含 buildx 插件，使用经典构建命令即可，`--platform` 在原生架构下不改变构建结果。

不得在 ARM 设备上构建 x86 镜像用于日常开发。指令集模拟会使 OpenCV 与 PyTorch 的运行速度下降三至十倍，并可能出现非法指令错误。若需要发布同时包含两种架构的镜像清单，应使用 `--platform linux/amd64,linux/arm64 --push`，该流程属于发布环节，不用于日常开发。

### 5.3 运行方式

```bash
docker run --rm -it \
  --network none \
  -v "$PWD/data:/app/data" \
  -v "$PWD/reports:/app/reports" \
  -v docnorm-cache:/cache \
  docnorm:cpu-arm64 predict --input data/raw_samples/01_ppt_text --model cnn
```

网页演示需映射端口，并允许本机访问：

```bash
docker run --rm -it \
  -p 127.0.0.1:8000:8000 \
  -v "$PWD/data:/app/data" \
  -v "$PWD/reports:/app/reports" \
  -v docnorm-cache:/cache \
  docnorm:cpu-arm64 uvicorn web.app:app --host 0.0.0.0 --port 8000
```

原型阶段直接以 Uvicorn 启动网页服务；命令行子命令 `docnorm serve` 在后续版本补充。网页模式只绑定本机回环地址，不对外网开放。结果写入容器内临时目录并定时清理，不写入数据集。

推理默认禁用网络，既减少外部依赖，也可证明未调用在线识别接口。首次运行需下载 torchvision 预训练权重，权重保存在命名卷 `docnorm-cache` 中，后续可离线使用。权重下载应在一次性容器中联网完成，并在报告中记录权重的校验和。

YuNet 人脸检测模型同样须在联网的一次性步骤中下载，由 `scripts/download_weights.py` 校验 SHA-256 后放入缓存卷，容器内映射至配置的 `models/` 路径。模型缺失或校验失败时自动降级为级联分类器并记录日志，见 ADR-0007。模型文件不纳入版本控制。

### 5.4 外置卷说明

本项目数据位于外置卷。Docker Desktop 对该路径的绑定挂载存在明显读写开销，训练阶段尤为明显。可采用以下两种方式缓解。

1. 将数据复制到命名卷中，例如 `docker cp data docnorm-dev:/app/data`，后续通过同步脚本更新。
2. 训练前将数据复制到容器可写层，训练结束后仅将产物复制回宿主机。

## 6. 数值一致性措施

| 措施 | 具体做法 |
|---|---|
| 固定随机种子 | 入口统一使用种子 42，同时设置 `random`、`numpy` 与 `torch` 的种子 |
| 固定线程数 | 设置 `OMP_NUM_THREADS=1`，并调用 `torch.set_num_threads(1)` |
| 确定性算子 | 启用 `torch.use_deterministic_algorithms(True, warn_only=True)` |
| 评估设备 | 强制使用中央处理器，即使设备具备 MPS 或 CUDA |
| 数据顺序 | 评估阶段关闭打乱，数据加载进程数设为 0 |
| 图像解码 | 统一使用彩色读取模式，并依据元数据校正方向 |
| 版本记录 | 将依赖快照写入对应实验目录的 `env.txt` |

允许的差异范围为：准确率绝对差不超过 0.5 个百分点；混淆矩阵允许一至两个样本位移，但须在复现记录中说明。

## 7. 训练设备策略

| 设备 | 允许用途 | 说明 |
|---|---|---|
| 中央处理器，容器内 | 全部正式评估 | 唯一的可比口径 |
| Apple MPS | 个人调参与快速试验 | 须记录设备；部分算子回退至中央处理器，可能反而更慢 |
| NVIDIA CUDA | 组员本地训练 | 须在报告中声明；不得用于最终指标对比 |

推理与评估统一在容器内以中央处理器执行，避免因设备不同导致指标不一致。

## 8. 已知问题

| 现象 | 原因 | 处理方式 |
|---|---|---|
| 导入 OpenCV 报二进制接口错误 | NumPy 2.x 与旧版 OpenCV 不匹配 | 锁定 `opencv-python-headless>=4.10` 与 `numpy>=1.26` |
| 安装 PyTorch 时下载体积过大 | 默认源包含 CUDA 组件 | 使用中央处理器版本索引 |
| Windows 无 docker 命令 | 未安装 Docker Desktop 或未启用 WSL2 | 改用按平台锁定依赖，或使用共用虚拟机 |
| 容器内中文文件名异常 | 宿主机压缩包编码不一致 | 使用版本控制获取文件，或以 UTF-8 编码解压；文件名尽量使用 ASCII 前缀 |
| Windows 路径过长 | 目录层级过深或文件名过长 | 将仓库置于较短路径下 |
| macOS 挂载目录训练缓慢 | Docker Desktop 文件共享机制 | 将数据复制至容器卷内 |
| 权重下载超时 | 网络环境受限 | 预先下载至缓存卷，并记录来源 |
| 缺少 `libGL.so.1` | 安装了带图形界面的 OpenCV | 使用无图形界面版本 |
| 同一代码在不同设备上结果相差较大 | 划分文件不一致 | 划分文件纳入版本控制，评估前校验哈希 |
| 图表中文显示为方块 | 容器缺少中文字体 | 镜像安装 Noto 中文字体，并在绘图配置中指定字体 |
| YuNet 模型缺失或校验失败 | 未执行下载脚本或网络受限 | 自动降级为级联分类器，并在日志中告警；补齐模型后重新运行 |

## 9. 备用方案：共用 Linux 虚拟机

适用场景包括：深度学习训练超过两小时、组员设备性能不足、需要统一的可访问环境。建议配置为 8 个虚拟处理器、16 GB 内存、100 GB 存储，可不配置图形处理器。系统采用 Ubuntu 22.04 长期支持版本。访问方式为 SSH 配合终端复用工具，保证长任务不因断线中断。每名组员使用独立的环境或容器。数据存放于虚拟机内的统一目录，通过同步工具与本地保持一致。该方案存在单点故障风险，须每周备份样本清单与实验产物。

## 10. 环境验收

新成员加入后须在 30 分钟内完成以下验证。全组环境门禁定于 11 月 26 日，未通过者当日改用共用虚拟机或按平台锁定依赖方案。arm64 验证记录见 `reports/env_validation.md`；x86 由组员机器或共用虚拟机补测。

```bash
# 1. 检查命令行工具可用
docker run --rm -it docnorm:cpu-arm64 --help

# 2. 环境自检，阶段一提供 scripts/env_smoke.py
python scripts/env_smoke.py --json

# 3. 功能冒烟。M0 门禁以读写临时图像验证 OpenCV 与 NumPy
python -c "import cv2, numpy as np; p='/tmp/smoke.png'; cv2.imwrite(p, np.zeros((64,64,3), np.uint8)); assert cv2.imread(p) is not None; print('smoke ok')"
# 阶段一实现后，以真实样本复核：python -m docnorm.cli rectify --input data/raw_samples/00_inbox --limit 5
```

通过标准为三条命令均返回退出码 0，且环境自检报告的处理器架构与本机一致。

## 11. 复现说明模板

交付给评审的复现说明应包含以下内容。

```text
环境：Docker 24 及以上；镜像 docnorm:cpu，架构 arm64 或 amd64
步骤：
  1. 获取仓库并进入目录
  2. 构建镜像
     docker buildx build --platform linux/<架构> -t docnorm:cpu .
  3. 执行评估
     docker run --rm -v $PWD/data:/app/data -v $PWD/reports:/app/reports \
       docnorm:cpu evaluate --split data/splits/split_v2.json \
       --pred reports/predictions.csv
预期：准确率与 reports/metrics.json 一致，偏差不超过 0.5 个百分点
```
