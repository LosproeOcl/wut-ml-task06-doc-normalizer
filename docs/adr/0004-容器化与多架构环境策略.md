# ADR-0004：采用多架构原生容器并统一评估设备

- 状态：已接受
- 日期：2026 年 11 月 25 日
- 决策人：余青阳、李念
- 相关文档：`08-跨平台环境与复现方案.md`，非功能需求 NFR-02、NFR-03

## 背景

组员设备涵盖 ARM64 的 macOS 与 AMD64 的 Windows、Linux 三类。若各自安装依赖，将出现依赖版本漂移、预编译包不兼容与指标不可比三类问题。此前的跨课程协作中已出现同类问题，即使采用容器，不同架构之间的行为差异仍需专门处理。

## 备选方案

| 方案 | 一致性 | 搭建成本 | 主要风险 |
|---|---|---|---|
| 多架构原生容器 | 高 | 中等 | Windows 需 WSL2；镜像体积约 1.5 GB |
| 按平台锁定依赖 | 中等 | 低 | 系统库问题仍需逐台解决 |
| 共用 Linux 虚拟机 | 很高 | 中等 | 单点故障；依赖网络质量 |
| 各自安装依赖 | 低 | 最低 | 不可接受 |

## 决策

1. 主方案为多架构原生容器。以官方 `python:3.11-slim` 为基础，分别构建 `linux/arm64` 与 `linux/amd64` 镜像，不使用指令集模拟。
2. 正式评估统一在中央处理器上执行。无论设备是否具备 MPS 或 CUDA，报告指标一律取自容器内的中央处理器环境。
3. 训练允许异构。可使用 MPS 或 CUDA 进行调参，但须在报告中声明设备，最终模型须在中央处理器容器内复评。
4. 长时训练可提交至组内 Linux 虚拟机。
5. 按平台锁定依赖仅作兜底方案，其结果仅用于成员自查。

## 理由

1. 原生构建直接消除架构不匹配问题，无须依赖文档约束成员行为。
2. 统一中央处理器评估消除了不同加速设备之间的数值差异，使 85% 的结论对所有评审可复现。
3. 仅安装中央处理器版 PyTorch，可避免 CUDA 依赖使镜像体积膨胀数倍。
4. 以禁用网络的方式运行推理，可客观说明系统未调用在线识别接口。

## 后果

1. 11 月 26 日前须完成双架构冒烟测试。该测试为 M0 里程碑的出口条件，未通过则整体计划顺延，并在当日决定是否改用共用虚拟机。
2. 训练速度受限于中央处理器，须按 ADR-0003 的轻量方案执行。
3. 镜像构建方式与权重缓存策略须写入文档，见 `08-跨平台环境与复现方案.md` 第 5 节。
4. 若后续引入仅在 x86 架构可用的依赖，须重新评估方案并补充架构决策记录。
