# 工程规范与协作流程

| 项目 | 内容 |
|---|---|
| 文档编号 | T06-ENG-001 |
| 版本 | v1.0 |
| 适用范围 | 所有提交代码与文档的组员 |

## 1. 分支模型

采用简化的 Git Flow 模型。分支类型与用途如下。

| 分支 | 用途 | 生命周期 |
|---|---|---|
| `main` | 可运行、可复现的稳定版本 | 长期保留，设置保护 |
| `feat/<模块>-<简述>` | 新功能 | 合并后删除 |
| `fix/<简述>` | 缺陷修复 | 合并后删除 |
| `data/<批次>` | 样本清单、划分与数据说明的更新 | 合并后删除 |
| `docs/<简述>` | 文档修订 | 合并后删除 |

具体规则如下。

1. 禁止直接向 `main` 分支推送。M0 阶段仓库初始化与设计文档修订可由项目负责人直接提交至 `main`；阶段一开始后一律经合并请求。
2. 每个合并请求须至少一人评审。涉及指标口径的请求须由评估负责人评审。
3. 合并请求标题须包含模块前缀，例如 `[rectify] 增加面积校验`。
4. 合并方式采用压缩合并，保持主干历史线性可读。

## 2. 提交信息规范

提交信息采用约定式格式，结构如下。

```text
<类型>(<范围>): <摘要>

<正文，可选>

<附注，可选>
```

类型取值如下。

| 类型 | 用途 |
|---|---|
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `docs` | 文档 |
| `data` | 样本清单、划分与数据说明 |
| `exp` | 实验配置与结果记录 |
| `refactor` | 重构，不改变外部行为 |
| `test` | 测试 |
| `chore` | 依赖、构建与工程脚手架 |

示例：

```text
feat(rectify): 顶点排序增加面积校验
fix(eval): 修正类别缺失时宏平均 F1 的计算
data(manifest): 登记 P03 第二批 30 张样本
```

不得使用“更新”“修改”“最终版”等无信息量的提交信息。

## 3. 目录与命名

1. 包名使用小写字母与下划线，例如 `docnorm`、`rectify`、`classify`。
2. 单个模块职责单一，单个文件建议不超过 400 行。
3. 数据文件与运行产物不得放入源码目录。
4. 实验产物统一存放于 `runs/<实验编号>/`。该目录不纳入版本控制，仅将指标文件与配置快照的副本归档至 `reports/`。
5. 中文文件名仅允许出现在文档目录与样本目录。代码与配置文件一律使用 ASCII 字符。

## 4. 代码风格

| 项目 | 约定 |
|---|---|
| Python 版本 | 3.11 |
| 格式化 | `ruff format`，行宽 100 |
| 静态检查 | `ruff check`，启用 E、F、I、N、UP、B 规则 |
| 类型注解 | 公共函数必须标注参数与返回值类型 |
| 文档字符串 | 采用 Google 风格，可使用中文 |
| 随机性 | 所有入口接受随机种子参数，默认值 42 |
| 路径处理 | 使用 `pathlib.Path`，不得以字符串拼接构造路径 |
| 日志 | 库代码使用 `logging`，不得使用 `print`。命令行输出除外 |

## 5. 分析脚本管理

探索性分析可在 Notebook 中进行，但须遵守以下约定。

1. Notebook 仅用于探索与绘图草稿，不承载最终结论。
2. 报告中引用的全部数值，须能由 `src/` 下的脚本复现。
3. Notebook 提交前清空输出，或仅保留关键图表，避免仓库体积膨胀。

## 6. 实验管理

本项目不引入在线实验管理平台，采用配置快照与结果表相结合的方式。

```text
runs/exp-20261128-01/
├── config.snapshot.yaml   本次实际生效配置
├── metrics.json           指标
├── predictions.csv        预测结果
├── confusion_matrix.png   混淆矩阵
└── train.log              训练日志
```

`reports/experiments.csv` 每行记录一次实验，字段为实验编号、日期、执行人、模型、特征、输入、准确率、宏平均 F1 与备注。

实验编号格式为 `exp-日期-序号`，例如 `exp-20261128-01`。未登记于该表的实验结果不得写入报告。

## 7. 评审清单

评审人须检查以下事项。

- 是否存在数据泄漏，包括划分错误与标准化参数在训练集之外拟合。
- 随机性是否固定，随机种子是否记录。
- 指标实现是否符合 `06-评估与验收方案.md` 的口径，重点检查宏平均 F1 与混淆矩阵方向。
- 是否硬编码绝对路径或个人路径。
- 是否误提交大体积文件，包括图像、模型权重与运行产物。
- 新增依赖是否写入 `env/` 下的依赖文件。
- 失败分支是否可见，不得静默捕获异常。
- 对外使用的图像是否来自 `data/release/`，且存在对应的复核记录。

## 8. 持续集成计划

| 任务 | 触发条件 | 内容 |
|---|---|---|
| 静态检查 | 推送与合并请求 | 执行 `ruff check` 与格式检查 |
| 单元测试 | 推送与合并请求 | 执行 `pytest tests/unit`，不依赖网络 |
| 冒烟测试 | 合并至主干的请求 | 以 20 张小样本运行矫正与推理，校验输出结构 |

持续集成在 `ubuntu-latest` 环境运行即可。`macos-latest` 作为每周定时任务，用于验证 ARM 架构兼容性。

## 9. 依赖变更

1. 新增依赖须说明用途、体积以及是否提供 ARM64 预编译包。
2. 修改依赖后须重建镜像，并在两种架构上各执行一次冒烟测试。
3. 依赖版本在 M1 结束时锁定，此后仅接受安全修复。

## 10. 学术规范

1. 引用他人代码须在文件头部注明来源与许可协议。
2. 使用预训练权重须在报告的实现细节部分声明。
3. 不得将公开数据集的样本混入自采数据。
4. 不得伪造实验数值。所有数值须有对应的运行产物支撑。
5. 不得在报告、演示文稿与仓库中引用未经打码的原始样本。
